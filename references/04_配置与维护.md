# 04 · 配置与维护

## 核心设计

### 1. 四层分类结构

iCost 的分类**不是扁平的**，而是 **账本 › 收支方向 › 一级 › 二级**：

```
日常/收入 › 支出 › 日常餐饮 › 日常三餐
日常/收入 › 收入 › 其他     › 退款
情感社交  › 支出 › 朋友社交 › 礼金
```

**关键约束：每个账本的分类互相独立。** 只有「转账 / 还款 / 其他支出」跨账本共用。
归类时先定账本和方向，再选分类，顺序不能反。

> 分类体系**必须**从 App 内「设置 → 分类管理」**截图**逐字录入，
> 不能从历史数据反推 —— 历史只反映"用过的"，反映不了"配过的"。
> 实测截图比历史多出 8 个 0 笔记录的分类（麻将k歌、挂号费用、大额聚餐…）。

### 2. 账户归属自动解析

账单文件的 `支付方式`（微信）/ `收付款方式`（支付宝）字段**直接写明资金来源**：

| 账单原始值 | 映射账户 |
|---|---|
| 零钱通 / 零钱 | 「消费」微信 |
| 某银行储蓄卡(0001) | 「消费」某银行储蓄卡 |
| 某银行储蓄卡(0002) | 「应急」某银行储蓄卡 |
| 账户余额 | 「消费」支付宝 |
| 花呗 | 「消费」花呗 |
| 余额宝 | 「临时」余额宝「攒着」 |

**组合支付**用 `&` 分隔，取第一个真实账户：

```
建行(0001)&红包&遇财神立减  →  「消费」某银行储蓄卡
```

> **为什么不用追踪"微信零钱 vs 银行卡"**：
> 账单文件本身就告诉你扣的是哪张卡，不需要人工核对。
> 而且账户维度回答的是"资金结构"（钱在哪、怎么流），不是"支付通道细节"。

### 3. 五层归类策略

按顺序匹配，**命中即停**：

| 层 | 说明 | 覆盖 | 维护成本 |
|---|---|---|---|
| **L1 语义规则** | 高确定性关键词（`12306`→交通、`国网`→水电） | ~30% | 编辑 `rules.json` |
| **L2 商家映射** | 品牌名（`海底捞`、`乐仁堂`） | ~15% | 编辑 `merchant_map.json` |
| **L3 历史学习** | 从已有账单自动提取判别词（出现 ≥3 次、纯度 ≥85%） | ~35% | **自动** |
| **L4 品类词** | 通用商品类别（`海鲜｜自助｜烤肉`） | ~15% | 编辑 `rules.json` |
| **L5 平台兜底** | 电商平台（`京东｜淘宝`） | ~5% | 编辑 `rules.json` |

**实测 91% 自动完成**（76 笔中 69 笔）。需人工的 7 笔全是转账 / AA —— 这类本质上就该人工判断。

**为什么必须用语义理解而不是查表**：实测 1,461 个商户里 **1,249 个（85.5%）只出现过 1 次**，
查表法必然失效；而 **69.2% 的备注自带品类信息**（"牛阿良牛肉汤烧饼"、"国网陕西电力生活缴费"），
这才是准确率的真正来源。

### 4. 三重去重

| 类型 | 规则 |
|---|---|
| AA 合并 | 同日 ≥3 笔、时间跨度 <1 小时、金额相同的小额收入 → 合成 1 笔 |
| 与已有数据去重 | 以「日期 + 金额绝对值」为键匹配 iCost 现有记录 |
| 平台内去重 | 依赖 iCost 的「删除该次导入的所有账单」，导错可整批撤销 |

## 配置文件逐个说明

### `categories.json` — 四层分类树

```json
{
  "日常/收入": {
    "支出": { "日常餐饮": ["日常三餐", "水果", "..."], "...": [] },
    "收入": { "主业收入": ["日常工资", "公积金"], "...": [] }
  }
}
```

换分类体系只改这一个文件，其余逻辑不变。

### `accounts.json` — 账户体系

```json
{ "日常消费账户": { "accounts": [ {"name": "「消费」微信", "bal": 166, "hist": 1005} ] } }
```

命名规范 `「角色」具体账户名`。字段：`name` / `bal`（余额）/ `hist`（历史笔数）/ `main`。

### `pay_mapping.json` — 支付方式 → 账户

```json
{ "匹配": "某银行0001", "账户": "「消费」某银行储蓄卡", "优先级": 10 }
```

支持"非账户关键词"黑名单（红包 / 立减 / 券），组合支付会自动跳过。

### `rules.json` — 归类规则

```json
{
  "规则": [
    { "匹配": "健身房|私教|瑜伽", "账本": "成长提升", "方向": "支出",
      "一级": "运动健身", "二级": "健身", "依据": "运动健身", "置信": "高" }
  ],
  "品类词": { "...": [] },
  "平台兜底": { "...": [] },
  "美团特殊处理": { "餐饮": [], "美业": [], "运动": [] }
}
```

**越具体的规则放越前面** —— 引擎按数组顺序匹配，先命中先返回。

### `merchant_map.json` — 商家名 → 分类

```json
"海底捞": ["日常/收入", "支出", "日常餐饮", "日常三餐"]
```

**每次在确认页发现归类不对，就把商家名加进来。** 这是准确率从 68% → 91% 的关键。

### `import_fix.json` — 人工修正表 + 导入开关

四个部分：

| 键 | 作用 |
|---|---|
| `cat_map` | 已归档分类的重映射（如「购物」→「其他支出」） |
| `patch` | 按 `日期｜金额` 精确定位一行，补字段。可加 `操作` 字段写手工补录指引 |
| `drop` | 直接剔除（去重用） |
| `_导入选项.冲减类型可导入` | 默认 `false`，冲减类走手工补录 |

```json
{
  "_导入选项": { "冲减类型可导入": false },
  "cat_map": { "购物": { "to": "其他支出", "c2": "", "原因": "已归档" } },
  "patch": [ { "key": "2026/10/16 07:44:20|1867",
               "set": { "类型": "退款入账", "账本": "成长提升",
                        "一级分类": "运动健身", "二级分类": "健身",
                        "备注": "健身房停业退款｜原订单 09/28 充值 2000",
                        "操作": "切到「成长提升」→ 长按 09/28 那笔 → 退款 1867" },
               "原因": "退款是冲减不是收入；账本必须跟原订单一致" } ],
  "drop": [ { "key": "2026/10/05 11:58:06|10.14", "原因": "微信/支付宝双边重复" } ]
}
```

### `icost_template.xlsx` — 官方模板骨架

App 内下载的原版导入模板，`export_split.py` 拿它当骨架克隆。
**别删、别改**。丢了就得重新从 App 里导出一份。

## 确认页功能

`output/记账确认.html`：

| 功能 | 说明 |
|---|---|
| 四层联动选择 | 账本 → 方向 → 一级 → 二级，逐级过滤，不会出现无效选项 |
| 快捷选项 | 转账 / AA 类给出「借出 / 还款 / AA分摊 / 礼金」等预设判断 |
| 补充说明 | 每笔可写文字 + 20 个快捷标签（退款 / 报销 / 垫付 / AA / 借出…） |
| **自动保存** | localStorage 实时存（KEY `icost_confirm_v3`），刷新/误关自动恢复 |
| 结果导出 | 固定底部弹窗，不受页面长度影响；支持复制 / 下载 txt |
| 未处理警告 | 漏掉的项会明确列出，不会静默丢失 |

## 已知限制

| 限制 | 说明 | 应对 |
|---|---|---|
| 分类树需手动维护 | 无法从账单推导，必须从 App 截图 | 换分类体系时重新截图 |
| 新商户首次必人工 | 品牌名无法推断 | 加进 `merchant_map.json` |
| 转账性质必人工 | 借出/还款/AA 无法从金额判断 | 确认页写一句说明 |
| 中文分词不完美 | 2-6 字滑窗 + 去冗余，可能有碎片 | 历史学习层持续补充 |
| 冲减类不能导入 | iCost 只认 支出/收入/转账 | 走 `手工补录清单.md` |
| 跨账本冲减做不到 | 账本间分类独立 | 账本必须跟原订单一致 |
